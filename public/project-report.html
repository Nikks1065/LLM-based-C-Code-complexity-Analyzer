1. EXECUTIVE SUMMARY & ABSTRACT

Software maintenance consumes the preponderance of lifecycle expenditures in modern software engineering projects, often reaching 60% to 80% of total budgetary allocation. In systems programming languages such as C, structural complexity—characterized by deeply nested conditional logic, unconstrained pointer manipulation, and undocumented dynamic memory allocations—substantially elevates cognitive overhead, defect density, and security vulnerabilities. Traditional static analysis tools (e.g., splint, pmccabe, complexity) compute raw metrics but leave remediation entirely to human intuition. Conversely, modern Large Language Models (LLMs) can generate semantic code summaries but often hallucinate mathematical metrics and provide unvalidated code transformations.

This academic project presents the design, formalization, and implementation of the LLM-Based C Code Complexity & Architectural Analyzer. The system establishes a novel, hybrid software engineering architecture that marries deterministic client-side Abstract Syntax Tree (AST) static analysis with neural generative reasoning. The deterministic core implements exact algorithms for:

  • McCabe Cyclomatic Complexity ($V(G)$) via graph-theoretic decision points;
  • Halstead Software Science (Vocabulary, Length, Volume, Difficulty, Effort, Time, Latent Bugs);
  • Lines of Code (LOC) breakdown (Physical, Logical, Blank, Comment Ratios);
  • Software Engineering Institute (SEI) Maintainability Index on a standardized 0–100 scale;
  • Asymptotic Algorithmic Complexity (Big-O Time & Space) via loop depth and recursion tracing;
  • Memory Safety Heuristics tracking unmanaged malloc invocations and dangerous C library functions.

The verified structural metrics are subsequently coupled with zero-hallucination prompt schemas transmitted to Google Gemini 2.5 Flash through an authenticated server proxy. The platform synthesizes semantically equivalent, refactored C code with lower complexity, displays line-by-line visual diffs with quantitative delta improvements, and offers an interactive architectural chat assistant. The entire software solution has been verified with 12 automated test suites, pushed to GitHub, and hosted on Render.

2. INTRODUCTION & BACKGROUND

2.1 Background of the Problem

Originating from the pioneering work of Dennis Ritchie at Bell Labs between 1969 and 1973, the C programming language continues to serve as the bedrock of global computing infrastructure. It underpins operating system kernels (Linux, FreeBSD, Windows NT), virtualization hypervisors, telecommunication routing switches, embedded flight control computers, and industrial control systems. C's enduring prominence stems from its minimal runtime overhead, predictable execution characteristics, and direct hardware memory addressing capabilities.

However, the very mechanisms that endow C with its high performance also expose software engineers to critical vulnerabilities:

  • Manual Resource Management: Absence of native garbage collection necessitates manual synchronization between malloc, calloc, and free, frequently culminating in memory leaks, double frees, and dangling pointers.
  • Procedural Sprawl: Historical legacy C codebases frequently accumulate monolithic subroutines extending across hundreds of lines, characterized by tangled switch-case dispatches and deeply nested loop hierarchies.
  • Cognitive Saturation: As control flow complexity expands exponentially, human maintainers struggle to form a reliable mental model of state transitions, precipitating severe regression defects during updates.

2.2 Motivation & Industry Context

Software maintenance costs are intimately linked to code comprehensibility. According to Lehman's Laws of Software Evolution, an evolving software system must undergo continuous structural refactoring to prevent entropy from rendering maintenance economically unfeasible. When McCabe Cyclomatic Complexity exceeds an index of 10, defect rates surge exponentially.

Traditional command-line linters provide static tabular outputs. While mathematically correct, they create an Actionability Gap: an alert stating main() has Cyclomatic Complexity 22 fails to tell a software engineer how to decompose the function safely without breaking pointer lifetimes. Meanwhile, purely generative AI assistants exhibit a Hallucination Deficit: when asked to compute cyclomatic complexity, models routinely invent edges or skip boolean predicates, yielding wildly inconsistent metrics.

Our motivation is to establish an integrated workbench where deterministic static analysis provides infallible ground truth, and Large Language Models provide contextual code refactoring and natural language explanations grounded by those exact metrics.

2.3 Scope of the Project

The scope of this project encompasses:

  1. Designing and implementing an in-browser ANSI C Lexer and AST Parser in TypeScript without relying on external native binaries or GCC installations.
  2. Developing mathematically rigorous computational engines for McCabe Cyclomatic Complexity, Halstead Software Science, LOC, SEI Maintainability Index, and Big-O Time/Space complexity.
  3. Building static heuristic checks for common security smells (memory leaks, unmanaged pointers, dangerous standard library calls).
  4. Creating a secure Node.js/Express backend service to proxy and format interactions with the Google Gemini 2.5 Flash model.
  5. Implementing an automated comparative refactoring engine that validates new code, computes metric deltas ($\Delta V(G)$, $\Delta MI$, $\Delta \text{LOC}$), and renders visual diffs.
  6. Deploying the platform to a public cloud PaaS (Render) with version-controlled continuous deployment from GitHub.

2.4 Practical and Industrial Applications

The practical utility of this software engineering platform spans multiple industrial and educational domains:

  • Continuous Integration / Continuous Deployment (CI/CD): Serving as an automated quality gate that blocks pull requests when cyclomatic complexity exceeds predefined engineering thresholds or when Maintainability Index deteriorates.
  • Safety-Critical Standards Compliance: Assisting teams in satisfying automotive (ISO 26262), aerospace (DO-178C), and railway standards (EN 50128), which mandate strict cyclomatic bounds ($V(G) \le 10$) on all production subroutines.
  • Engineering Education: Aiding undergraduate computer science students in visualizing how conditional branching, recursion, and nested loops physically drive algorithmic time complexity and maintainability degradation.
  • Legacy Modernization: Accelerating the refactoring of decades-old C codebases into clean, modular, and maintainable functional units.

4. THEORETICAL FOUNDATIONS & MATHEMATICAL FORMULATIONS

4.1 McCabe Cyclomatic Complexity

Formulated by Thomas J. McCabe in 1976 [1], Cyclomatic Complexity measures the number of linearly independent paths through a program's source code. A software routine is modeled as a strongly connected control flow graph $G = (V, E)$, where $V$ is the set of basic blocks (nodes) and $E$ is the set of directed control transfers (edges).

V(G) = E - N + 2P (Equation 1)

Where $E$ is the number of edges, $N$ is the number of nodes, and $P$ is the number of connected components ($P = 1$ for a single procedural subroutine).

In structured programming, McCabe demonstrated that $V(G)$ is identically equal to the sum of predicate decision points plus one:

V(G) = \sum_{i=1}^{k} D_i + 1 (Equation 1a)

Where each $D_i$ represents a syntactic decision point: if, else if, for, while, do-while, case, ternary expressions (? :), and compound short-circuit boolean operators (&&, ||).

Cyclomatic Score Structural Risk Tier Testability & Maintainability Implications
1 – 10 Low Risk (Simple) High testability, clear cognitive structure, low defect rate.
11 – 20 Moderate Risk Moderately complex; requires substantial unit test suites.
21 – 50 High Risk (Complex) Difficult to test and maintain; elevated defect density.
> 50 Untestable (Very High) Severe technical debt; candidate for total architectural rewrite.

4.2 Maurice Halstead Software Science Metrics

Introduced in 1977 [2], Halstead metrics measure the software's structural scale through operator and operand counting:

  • $\eta_1$ = Count of distinct (unique) operators (e.g., +, *, if, ->, =).
  • $\eta_2$ = Count of distinct (unique) operands (variable identifiers, constants).
  • $N_1$ = Total count of operator occurrences.
  • $N_2$ = Total count of operand occurrences.

From these basic quantities, the following software science metrics are computed:

\text{Program Vocabulary: } \eta = \eta_1 + \eta_2 \quad \text{and} \quad \text{Length: } N = N_1 + N_2 (Equation 2)
\text{Program Volume: } V = N \times \log_2(\eta) (Equation 3)
\text{Program Difficulty: } D = \left(\frac{\eta_1}{2}\right) \times \left(\frac{N_2}{\eta_2}\right) (Equation 4)
\text{Mental Effort: } E = D \times V = \left(\frac{\eta_1}{2} \cdot \frac{N_2}{\eta_2}\right) \times \left(N \log_2 \eta\right) (Equation 5)
\text{Estimated Time to Code: } T = \frac{E}{18} \text{ seconds} (Equation 6)
\text{Projected Latent Bugs: } B = \frac{V}{3000} (Equation 7)

4.3 Maintainability Index (SEI / Oman-Hagemeister Model)

The Maintainability Index ($MI$) is an empirical composite index designed by Oman and Hagemeister [3] and adopted by the Software Engineering Institute (SEI) [4]. It balances Halstead Volume, Cyclomatic Complexity, LOC, and comment density:

MI_{\text{raw}} = 171 - 5.2 \ln(V) - 0.23 V(G) - 16.2 \ln(\text{LOC}) + 50 \sin\left(\sqrt{2.4 \times \text{perCM}}\right) (Equation 8)

Where $V$ is Halstead Volume (Eq. 3), $V(G)$ is McCabe Complexity (Eq. 1), $\text{LOC}$ is non-empty code lines, and $\text{perCM}$ is the comment percentage ($\text{CommentLines} / \text{LOC}$).

To produce a clean engineering metric between 0 and 100, the score is normalized:

MI = \max\left(0, \min\left(100, \frac{MI_{\text{raw}} \times 100}{171}\right)\right) (Equation 8a)

4.4 Asymptotic Algorithmic Complexity (Big-O Time & Space)

Asymptotic analysis evaluates algorithmic resource consumption as input scale $N \to \infty$. Our parser models iteration depth as:

T(N) = \max_{k \in \text{loops}} \left( \prod_{d=1}^{D_k} \text{StepComplexity}(d) \right) + \text{RecursionFactor} (Equation 9)

Linear loop increments ($i++$) contribute $O(N)$, geometric loops ($i = i * 2$ or $i = i / 2$) contribute $O(\log N)$, and self-invoking dual-recursive procedures (e.g., recursive Fibonacci) are flagged as exponential $O(2^N)$.

6. DETAILED IMPLEMENTATION & SOFTWARE ENGINEERING

6.1 Lexical Scanner & AST Parser Implementation

The lexical scanner (src/analyzer/cLexer.ts) processes raw C source code character-by-character, transforming it into a strongly typed token array. It handles string literals, character constants, multi-line C-style comments (/* ... */), and preprocessor commands without dropping token line numbers.

The parser (src/analyzer/cParser.ts) identifies top-level functions using bracket-depth counters ($depth = 0 \to 1$). When a function signature is matched, the parser creates a ParsedFunction record containing:

  • name, returnType, and parameters;
  • startLine and endLine in the source buffer;
  • Sub-array of tokens belonging exclusively to that function;
  • Extracted local variable declarations and function calls.

6.2 Static Quality Smells & Memory Leak Detector

The module src/analyzer/qualityFindingsAnalyzer.ts performs AST rule checks:

  • Memory Leak Audit: Tracks dynamic allocation tokens (malloc, calloc, realloc). If the token occurs without a matching free() call referencing the assigned pointer, a High Severity memory leak warning is registered.
  • Deep Nesting Detection: Iterates through statement block braces; any code executing at brace depth $\ge 4$ triggers a Medium Severity cognitive overload warning.
  • Unbounded C Library Calls: Scans for deprecated functions (gets, strcpy, sprintf) and flags potential buffer overflow vulnerabilities (CWE-120).

6.3 Google Gemini LLM Integration & Prompt Engineering

In src/services/geminiService.ts, the application interfaces with @google/genai. To prevent generic or hallucinated responses, the prompt embeds the verified metrics: 

You are an expert Principal Systems Engineer and C Compiler Architect.
Analyze the following C source code along with its DETERMINISTIC static metrics:
- Overall Cyclomatic Complexity: ${analysis.cyclomatic.score} (${analysis.cyclomatic.riskLevel})
- Halstead Volume: ${analysis.halstead.volume} bits, Effort: ${analysis.halstead.effort}
- Maintainability Index: ${analysis.maintainability.score}/100
- Detected Code Smells: ${analysis.qualityFindings.map(f => f.title).join(', ')}

Refactor this code to achieve:
1. Cyclomatic Complexity strictly under 8 by extracting monolithic logic into static helper routines.
2. Eliminate all identified memory safety issues and ensure every malloc is paired with free.
3. Replace deeply nested conditionals with early-return guard clauses.
4. Maintain strict functional equivalence and preserve external function signatures.
Format response strictly as valid JSON adhering to the RefactoredCodePayload schema.

6.4 Delta Diff Engine & 1-Click Refactoring

When the refactored code arrives from the server, src/analyzer/diffHelper.ts executes the complete static analysis suite on both the original and new code. It calculates:

  • $\Delta V(G) = V(G)_{\text{new}} - V(G)_{\text{old}}$ (Target: Negative / Complexity Reduced)
  • $\Delta MI = MI_{\text{new}} - MI_{\text{old}}$ (Target: Positive / Maintainability Increased)
  • $\Delta \text{LOC} = \text{LOC}_{\text{new}} - \text{LOC}_{\text{old}}$

The user can view side-by-side split diffs with highlighted changes and click "Accept & Apply Refactoring" to overwrite the active editor buffer, which immediately recalculates all system dashboards.

8. DISCUSSION, STRENGTHS, AND LIMITATIONS

8.1 Interpretation of Findings

The experimental results demonstrate that grounding Large Language Models with deterministic static metrics effectively overcomes the weaknesses of both individual paradigms. The deterministic engine provides mathematical rigor, while the LLM delivers contextual code comprehension and semantic refactoring suggestions.

The delta comparison interface gives developers immediate visibility into the tangible benefits of refactoring, providing quantitative justification for code cleanups during peer code reviews.

8.2 Architectural Strengths

  • Zero-Latency Local Analysis: Parsing runs natively in the browser without requiring remote compilation servers.
  • Deterministic Mathematical Grounding: Metrics adhere strictly to established academic formulations (McCabe, Halstead, SEI-MI).
  • Safe, Rate-Monitored AI Proxy: Server-side proxy keeps Gemini API credentials secure while structuring inputs and outputs into validated JSON schemas.
  • Bidirectional Diff Verification: Every refactoring proposal is evaluated to prove complexity reduction before the user accepts changes.

8.3 System Limitations and Boundary Conditions

  • Preprocessor Macro Limitations: While basic macros are tokenized cleanly, the current parser does not execute a full preprocessor pass for complex parameterized macros.
  • Pointer Aliasing Undecidability: In accordance with Rice's Theorem, static determination of arbitrary runtime pointer aliasing is undecidable; our memory analyzer uses lexical scope heuristics rather than whole-program interprocedural analysis.
  • LLM Rate Limits: Very large monolithic files (> 3,000 LOC) may face token context window boundaries during full-file refactoring.

The LLM-Based C Code Complexity & Architectural Analyzer successfully bridges the gap between static software engineering metrics and neural generative AI. Appendix A: Core Cyclomatic Complexity Calculation Engine

// src/analyzer/cyclomaticAnalyzer.ts
export function analyzeCyclomaticComplexity(func: ParsedFunction, funcIndex: number): CyclomaticComplexityResult {
  let score = 1; // Base complexity V(G) = 1
  const decisionPoints: DecisionPoint[] = [];

  for (let i = 0; i < func.tokens.length; i++) {
    const token = func.tokens[i];

    // Branching Keywords
    if (token.type === 'KEYWORD') {
      if (token.value === 'if' || token.value === 'for' || token.value === 'while' || token.value === 'case') {
        score++;
        decisionPoints.push({
          line: token.line,
          type: token.value as any,
          description: `Branch point introduced by '${token.value}' statement`,
          complexityContribution: 1
        });
      }
    }

    // Compound Boolean Predicates & Ternary
    if (token.type === 'OPERATOR') {
      if (token.value === '&&' || token.value === '||') {
        score++;
        decisionPoints.push({
          line: token.line,
          type: 'logical_op',
          description: `Short-circuit boolean evaluation '${token.value}'`,
          complexityContribution: 1
        });
      } else if (token.value === '?') {
        score++;
        decisionPoints.push({
          line: token.line,
          type: 'ternary',
          description: `Conditional ternary operator '?'`,
          complexityContribution: 1
        });
      }
    }
  }

  const riskLevel = score <= 5 ? 'Low Risk' : score <= 10 ? 'Moderate Risk' : score <= 20 ? 'High Risk' : 'Very High Risk';
  return { score, decisionPoints, riskLevel };
}

Appendix B: SEI Maintainability Polynomial Engine

// src/analyzer/maintainabilityAnalyzer.ts
export function analyzeMaintainability(
  halsteadVolume: number,
  cyclomaticComplexity: number,
  linesOfCode: number,
  commentRatio: number = 0
): MaintainabilityResult {
  const safeVolume = Math.max(1, halsteadVolume);
  const safeLOC = Math.max(1, linesOfCode);
  const safeCC = Math.max(1, cyclomaticComplexity);
  const safeCommentRatio = Math.max(0, Math.min(1, commentRatio));

  // Standard SEI polynomial formulation
  const rawMI = 171
    - 5.2 * Math.log(safeVolume)
    - 0.23 * safeCC
    - 16.2 * Math.log(safeLOC)
    + 50 * Math.sin(Math.sqrt(2.4 * safeCommentRatio));

  // Normalize to 0-100 scale
  const normalizedScore = Math.max(0, Math.min(100, Math.round((rawMI * 100) / 171)));

  let rating: 'High' | 'Moderate' | 'Low';
  if (normalizedScore >= 80) rating = 'High';
  else if (normalizedScore >= 60) rating = 'Moderate';
  else rating = 'Low';

  return {
    score: normalizedScore,
    rawScore: Number(rawMI.toFixed(2)),
    rating,
    isMaintainable: normalizedScore >= 65
  };
}
